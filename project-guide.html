Data Analytics Capstone

Vendor Performance Analytics & Ledger·IQ

An end-to-end retail analytics project for an alcohol/beverage distributor: raw transaction CSVs are ingested into a SQL database, aggregated into a vendor-level summary with custom KPIs, explored statistically in Python, and surfaced in a Power BI dashboard — then extended with a deployed machine-learning app that forecasts freight and flags risky invoices.

01Overview

Elevator pitch: A wholesale beverage distributor buys from many vendors and sells thousands of brands. Profit lives or dies on which vendors and brands to back, how much to buy, and how much capital is frozen in unsold stock. This project takes the messy raw data — purchases, prices, sales, and freight invoices — and turns it into decisions: it builds a clean vendor-level summary in SQL, runs a full exploratory + statistical analysis in Python, and presents the findings in a Power BI dashboard. A second deliverable, Ledger·IQ, is a deployed Streamlit app that puts two machine-learning models in front of finance: one forecasts freight cost, the other flags invoices that don't reconcile with their purchase order.

What it does

  • Ingests raw CSVs into a SQLite database (one table per file)
  • Joins 4 tables into a single vendor-brand summary via SQL CTEs
  • Engineers profitability KPIs (margin, turnover, gross profit)
  • Runs EDA: distributions, correlations, outliers, data quality
  • Tests hypotheses (confidence intervals, t-test) on vendor margins
  • Visualizes it all in an interactive Power BI report
  • Ledger·IQ: ML freight forecast + invoice-risk classifier (live app)

Why it's interesting

  • Real, messy data — negative profits, infinities, missing values
  • Pipeline thinking: ingestion → transform → analyze → present
  • Set-based SQL (CTEs) instead of slow row-by-row Python
  • Findings backed by statistics, not just charts
  • A clear business narrative: concentration risk, dead stock, bulk pricing
  • An ML layer that closes the loop into operational decisions
Two deliverables, one storyThe analytics project explains what happened and why (descriptive + diagnostic). Ledger·IQ turns that understanding into what to do next (predictive + prescriptive). Together they walk the full analytics maturity ladder.

Live links: Power BI report (app.powerbi.com share link) · Ledger·IQ app at ledgeriq.streamlit.app.

03Architecture & Pipeline

The analytics project is a classic ELT pipeline: load raw files into a database, transform with SQL into an analysis-ready table, then analyze and present. Ledger·IQ is a parallel train-once / serve-many ML pipeline built on its own India logistics datasets.

RAW CSVs INGEST TRANSFORM (SQL) ANALYZE / PRESENT ┌──────────────┐ ┌──────────────────┐ ┌──────────────────────┐ ┌──────────────────┐ │ purchases │ │ ingestion_db.py │ │ get_vendor_summary.py│ │ Jupyter EDA │ │ purchase_ │ ───► │ for each *.csv: │ ──► │ CTEs: │ ─► │ + stats │ │ prices │ │ read_csv → │ │ FreightSummary │ │ ──────────────── │ │ sales │ │ to_sql(table) │ │ PurchaseSummary │ │ Power BI .pbix │ │ vendor_ │ │ │ │ SalesSummary │ │ dashboard │ │ invoice │ │ inventory.db │ │ → JOIN → clean → │ └──────────────────┘ └──────────────┘ │ (SQLite) │ │ add KPIs → │ └──────────────────┘ │ vendor_sales_summary│ └──────────┬───────────┘ │ exported ▼ vendor_sales_summary.csv (18 cols) ── Ledger·IQ (separate ML deliverable) ─────────────────────────────────────────────── India CSVs ─► preprocessing ─► train.py (sklearn pipelines) ─► .pkl + metadata.json │ Streamlit app.py ◄── inference/ (load .pkl) ◄──┘ ► ledgeriq.streamlit.app

Why a database + SQL, not pure pandas?

  • Set-based aggregation at the source — joining and grouping four large tables is what SQL engines are built for; doing it in SQL keeps memory low and the logic declarative.
  • One table per file — the ingestion script names each table after its CSV, so the schema mirrors the raw data and is easy to reason about.
  • Reproducibility — the summary is a single query; rerun it and you get the same analysis-ready table every time.
  • Separation of stages — ingestion, transformation, and analysis are independent scripts/notebooks that can be rerun in isolation.

04Components in Detail

ingestion_db.py — load raw data

Walks the data/ folder, reads every .csv into a pandas DataFrame, and writes it to inventory.db with df.to_sql(table_name, engine, if_exists='replace') — the table name is the filename without its extension. A SQLAlchemy engine (sqlite:///inventory.db) is the connection, and the whole run is timed and logged. Net effect: the four source tables (purchases, purchase_prices, sales, vendor_invoice) land in one database.

get_vendor_summary.py — build the analysis table

The heart of the transform. One SQL query with three CTEs stitches the tables together:

FreightSummary   → freight cost per VendorNumber           (from vendor_invoice)
PurchaseSummary  → purchase qty/$ per vendor·brand, joined  (purchases ⋈ purchase_prices)
                   to actual price & volume; PurchasePrice > 0
SalesSummary     → sales qty/$/price/excise per vendor·brand (from sales)

PurchaseSummary  LEFT JOIN SalesSummary  (on vendor+brand)
                 LEFT JOIN FreightSummary (on vendor)
ORDER BY TotalPurchaseDollars DESC

Then clean_data() casts Volume to float, fills missing values with 0, strips whitespace from VendorName/Description, and engineers four KPIs (below). The cleaned frame is written back into the DB as vendor_sales_summary and exported to vendor_sales_summary.csv.

Why LEFT JOIN from purchases?Every purchased brand should appear even if it never sold — those rows (sales = 0) are exactly the slow-moving / dead-stock items the analysis cares about. An inner join would silently hide them.

The notebooks — EDA & analysis

  • Exploratory Data Analysis.ipynb — first pass over the raw tables: shapes, dtypes, value ranges, relationships, deciding which columns matter.
  • Vendor Performance Analysis.ipynb — the deep dive on the summary table: distributions, correlation heatmap, outliers, the business questions, and the statistical tests. This is where the insights in §7 come from.

vendor_performance.pbix — the dashboard

Power BI Desktop report built on the summary table: KPI cards, top-vendor/brand bars, scatter of sales vs margin, and the procurement-concentration view. The shareable Power BI Service link is the stakeholder-facing deliverable.

Ledger·IQ — the ML app

A self-contained Streamlit project (in Inventory-Invoice-Analytics/) with two trained models, an inference layer, and a polished dark-themed UI. Covered in full in §10.

07The Analysis & Insights ★

This is the payload of the project — the business questions and what the data answered. Memorize a few of these numbers; they're what make the project concrete in an interview.

Summary-statistics findings

  • Loss-making transactions exist. Minimum GrossProfit is −52,002.78 — some brands sell below cost (deep discounts or mispricing).
  • Unsold stock. Min TotalSalesQuantity and SalesDollars are 0 — products purchased but never sold (slow-moving / obsolete).
  • ProfitMargin hits −∞ where revenue is zero or below cost — a data-quality flag handled in cleaning.
  • Premium-product outliers. Max PurchasePrice/ActualPrice (5,681 / 7,499) tower over the means (~24 / ~36) — a long-tail of high-end items.
  • Freight varies wildly — 0.09 to 257,032 — hinting at logistics inefficiency or bulk shipments.
  • StockTurnover 0 → 274.5 — some items fly off shelves, others sit indefinitely.

Correlation findings

  • Purchase qty ↔ sales qty = 0.999 — near-perfect; inventory generally turns over efficiently in aggregate.
  • PurchasePrice barely correlates with revenue/profit (−0.012 / −0.016) — price level alone doesn't drive sales.
  • ProfitMargin ↔ sales price = −0.179 — higher prices come with thinner margins (competitive pressure).
  • StockTurnover weakly negative with profitability — fast turnover ≠ more profit.

Business-question findings

  • Vendor concentration risk. The top vendors account for ~65.7% of total purchase dollars; the remaining vendors only ~34.3%. High dependency = supply risk → diversify suppliers.
  • Bulk purchasing pays off. Large-order vendors get the lowest unit price (~$10.78/unit), roughly a 72% reduction vs small orders — bulk pricing strategy works, if inventory is managed.
  • Promotion candidates. Brands with high margin but low sales volume are prime for promotions/price adjustments to lift volume.
  • Slow-moving inventory & locked capital. Vendors with low StockTurnover tie up capital in unsold stock and rack up holding costs (warehouse, insurance, depreciation) — flagged for action.
  • Top performers by sales are identified for both vendors and brands to focus commercial effort.
The counter-intuitive headlineLow-sales vendors have higher profit margins (95% CI ≈ 40.5%–42.6%) than top-selling vendors (≈ 30.7%–31.6%). Big sellers run on volume + thin margins; small vendors lean on premium pricing. The strategic move differs per group: high performers optimize cost/bundling; low performers need marketing & distribution, not more margin.

08Statistical Methods

What lifts this above a charting exercise: the conclusions are tested, not eyeballed.

95% Confidence intervals on profit margin

Computed separately for top-performing and low-performing vendor groups. The intervals don't overlap (≈30.7–31.6% vs ≈40.5–42.6%), which is the first signal the two groups are genuinely different — not noise.

Two-sample hypothesis test

H₀: mean profit margin (top) = mean profit margin (low)   — no difference
H₁: the means differ
Result: p-value ≪ 0.05  →  reject H₀

The tiny p-value says the margin gap is statistically significant, and its size makes it practically meaningful too — the two vendor segments really do operate on different economics, justifying different strategies.

How to talk about it"I didn't just notice small vendors looked more profitable — I quantified it with confidence intervals, then confirmed it with a two-sample t-test. Non-overlapping CIs plus a p-value far below 0.05 means I can defend that finding, not just assert it."

10Ledger·IQ — the ML Extension

A deployed Streamlit app (ledgeriq.streamlit.app) that turns the analytics into action for procurement finance. India-specific: costs in INR, trained on Indian logistics data. Two modules.

Module 1 — Freight Cost Forecast (Regression)

  • Goal: predict delivery/freight cost before the carrier bills you, for budgeting & sanity-checking quotes.
  • Data: India Delivery Logistics dataset, 25,000 rows.
  • Features: distance_km, package_weight_kg, delivery_mode, vehicle_type, package_type, region, weather_condition → target delivery_cost.
  • Pipeline: ColumnTransformer (StandardScaler on numerics + OneHotEncoder on categoricals) → model. Three candidates trained: Ridge, Gradient Boosting, Random Forest; the lowest-MAE model is saved.
  • Winner: Ridge Regression — MAE ≈ ₹1.58, RMSE ≈ ₹4.67, R² ≈ 99.99%.
Be honest about that R²99.99% is suspiciously perfect — the synthetic-ish logistics cost is almost a deterministic function of distance/weight/mode, so a linear model nails it. In an interview, say that: "the near-perfect R² tells me the target is largely a linear function of the inputs in this dataset; I'd validate on real held-out invoices before trusting it in production."

Module 2 — Invoice Risk Review (Classification)

  • Goal: flag invoices that don't reconcile with their purchase order so a human reviews them; auto-clear the rest.
  • Data: DTDC Courier India dataset, 49,639 rows. Real PO-vs-invoice data is sensitive (GSTIN/payment), so labels are synthetically derived by injecting controlled amount/quantity mismatches into ~38% of rows.
  • Base features: invoice_quantity, invoice_amount_inr, freight_inr, total_item_quantity, total_item_amount_inr. Engineered: amount_gap_inr, quantity_gap, freight_ratio — the reconciliation signals.
  • Model: RandomForestClassifier (220 trees, max_depth 10, class_weight='balanced') inside a StandardScaler pipeline; stratified split; tuned for F1.
  • Performance: Accuracy ≈ 99.1%, F1 ≈ 0.988.
Why F1 and class_weight, not accuracy alone?Risky invoices are the minority and missing one is costly (financial leakage). class_weight='balanced' stops the model from ignoring the rare class, and F1 balances precision (don't cry wolf on clean invoices) against recall (don't miss real risks).

The app & serving

  • train.py per module fits the pipeline, picks/saves the best model as .pkl + a metadata.json (dataset, features, metrics) for traceability.
  • inference/ loads the pickled pipeline and exposes predict_freight_cost() / predict_invoice_flag() — feature engineering re-applied identically at inference time.
  • app.py — a heavily custom-styled (dark "Modern Dark" theme) two-module Streamlit UI. Every prediction comes with a confidence meter, the evidence factors, and a plain-language recommended action — so finance trusts the call, not just the number.

13Interview Q&A

A bank of likely questions with detailed answers. Click any to expand.

Pipeline, Database & SQL
QWalk me through the data pipeline end to end.

It's an ELT flow. ingestion_db.py reads each CSV in data/ and loads it into a SQLite database as its own table via to_sql. Then get_vendor_summary.py runs one SQL query with three CTEs — FreightSummary, PurchaseSummary, SalesSummary — that aggregate the four source tables to a common grain and LEFT JOIN them into a vendor-brand summary. Python then cleans that result (cast, fillna, strip) and engineers four KPIs, writes it back as vendor_sales_summary, and exports a CSV. From there it's EDA in Jupyter and a Power BI dashboard, plus the Ledger·IQ ML app as a separate deliverable.

QWhy aggregate in SQL with CTEs instead of pandas?

The joins and group-bys are exactly what a SQL engine is optimized for — set-based operations close to the data, low memory, and declarative logic that reads like the business question. CTEs keep each aggregation (freight, purchases, sales) readable and independently checkable before the final join. pandas then only handles the lighter cleaning and feature engineering on the already-reduced table.

QWhy LEFT JOIN and not INNER JOIN in the summary?

Because I start from PurchaseSummary and LEFT JOIN sales — a brand that was purchased but never sold must still appear, with sales = 0. Those rows are the slow-moving and dead-stock items the analysis is specifically looking for. An inner join would silently drop exactly the records that carry the most business signal.

QExplain the three CTEs.

FreightSummary sums Freight per VendorNumber from vendor_invoice (freight is billed at the invoice/vendor level). PurchaseSummary joins purchases to purchase_prices on Brand to attach the actual price and volume, filters PurchasePrice > 0, and sums quantity and dollars per vendor·brand. SalesSummary sums sales quantity, dollars, price, and excise per vendor·brand. The final SELECT joins purchases→sales on vendor+brand and purchases→freight on vendor.

QWhy SQLite and SQLAlchemy?

SQLite is a zero-config embedded database — perfect for a single-analyst project: the whole DB is one file, no server to run. SQLAlchemy gives a clean engine abstraction so to_sql/read_sql_query work uniformly and the same code could point at Postgres later by changing the connection string.

EDA & Insights
QWhat was your most important insight?

That small, low-sales vendors run higher profit margins (~40–43%) than the big-volume vendors (~31%). It's counter-intuitive — you'd assume the top sellers are the most profitable. The big players win on volume with thin margins; the small ones lean on premium pricing. It matters because the right strategy differs per segment: optimize cost and bundling for the big vendors, but invest in marketing and distribution for the small ones rather than squeezing more margin.

QYou found ~66% concentration — why does that matter?

The top vendors supply about 65.7% of total purchase dollars, leaving ~34% across everyone else. That's concentration risk: if one major vendor raises prices, has a supply disruption, or changes terms, the business is heavily exposed. The recommendation is to evaluate alternative suppliers for the most depended-on categories to de-risk procurement.

QWhat did the correlation analysis tell you?

Purchase quantity and sales quantity correlate at 0.999 — inventory turns over efficiently in aggregate. Purchase price barely correlates with revenue or profit (≈ −0.01), so price level alone doesn't drive sales. And profit margin is mildly negatively correlated with sales price (−0.18), consistent with competitive pricing compressing margins on higher-priced items. I was careful to read these as associations, not causes.

QHow did you handle negative margins and infinities?

I didn't delete them — they're signal. Negative gross profit means selling below cost; a −∞ margin means zero revenue on purchased stock. The cleaning step fills NaNs with 0 and I call these out explicitly in the EDA as loss-makers and dead stock. They feed directly into the "locked capital" and "promotion candidate" recommendations.

QWhat's the bulk-purchasing finding?

Grouping vendors by order size, the large-order group gets the lowest unit cost — around $10.78/unit, roughly a 72% reduction versus small orders. So bulk pricing successfully incentivizes larger purchases. The caveat is inventory management: the savings only materialize if that bulk stock actually sells rather than becoming the slow-moving inventory I flagged elsewhere.

Statistics
QHow did you confirm the margin difference was real?

Two ways. First, 95% confidence intervals on each group's mean margin — low performers ≈40.5–42.6%, top performers ≈30.7–31.6%. They don't overlap, which is a strong hint. Then a two-sample hypothesis test on the means: the p-value came out far below 0.05, so I reject the null that the means are equal. The effect is both statistically significant and large enough to be practically meaningful.

QWhat does the p-value actually mean here?

It's the probability of seeing a margin gap this large (or larger) between the two vendor groups if there were truly no difference. A value far below 0.05 means that's very unlikely under the null, so I conclude the groups genuinely differ. I'm careful not to overclaim — it's evidence against "no difference," not proof of a specific cause.

QWhat are the assumptions/limits of that test?

A two-sample t-test assumes roughly independent samples and, classically, normal-ish means (the CLT helps at these sample sizes) and comparable variances — Welch's version relaxes the equal-variance assumption. With heavy outliers in margin I'd sanity-check with a non-parametric Mann–Whitney test too. And "top vs low" depends on how I defined the groups, so the cutoff is a choice I'd disclose.

Power BI
QWhy do the transforms upstream instead of in Power BI?

Keeping the joins, cleaning, and KPI logic in SQL/Python means the model Power BI imports is already clean and the logic is version-controlled and testable. Power BI then handles presentation and light DAX. It keeps the report fast, avoids duplicating business logic in DAX, and means the same summary feeds both the dashboard and the notebooks.

QWhat would a stakeholder do with the dashboard?

Slice performance by vendor and brand without touching code: see top vendors and the concentration share, spot high-margin/low-volume brands to promote, and find low-turnover vendors where capital is stuck. It turns my analysis into a self-serve tool, published as a link so viewers need nothing installed.

Machine Learning (Ledger·IQ)
QWalk me through the freight model.

It's a regression on India logistics data (25k rows) predicting delivery cost from distance, weight, and categorical factors like mode, vehicle, region, and weather. I built a sklearn pipeline: ColumnTransformer with StandardScaler on the numerics and OneHotEncoder on the categoricals, feeding the model. I trained Ridge, Gradient Boosting, and Random Forest and kept the lowest-MAE one — Ridge won, with MAE around ₹1.58 and an R² near 99.99%.

QThat R² is suspiciously high. What's going on?

Right — I flag that rather than celebrate it. In this dataset the delivery cost is almost a deterministic linear function of distance and weight, so a linear model essentially recovers the formula. It tells me the data is "too clean" / partly synthetic. Before trusting it operationally I'd validate on real held-out invoices and watch for leakage; I'd expect the real-world error to be meaningfully higher.

QHow does the invoice classifier work and how are the labels made?

It's a Random Forest that decides whether an invoice should auto-clear or be held for review. Public PO-vs-invoice data is sensitive, so I derive labels: take real India courier invoice charges and inject controlled amount/quantity mismatches into ~38% of rows to simulate PO/GRN discrepancies. The features are the raw invoice/PO fields plus engineered gaps — amount_gap, quantity_gap, freight_ratio. It scores ~99% accuracy and 0.988 F1.

QWhy F1 and class_weight='balanced' instead of accuracy?

Risky invoices are the minority class, and missing one means money leaks out. Plain accuracy would let the model look great by just predicting "clean" every time. class_weight='balanced' makes the rare class count more during training, a stratified split preserves the ratio, and F1 keeps precision and recall in balance — I want to catch real risks without flagging every clean invoice and burying analysts.

QHow is the model served, and how do you avoid train/serve skew?

train.py fits the full pipeline and pickles it with joblib alongside a metadata.json recording dataset, features, and metrics. The inference module loads that pickle and re-applies the exact same derived-feature logic before predicting, and because the scaler/encoder live inside the pickled pipeline, the same preprocessing runs at train and serve time. The Streamlit app calls those inference functions and renders the prediction with a confidence meter and a plain-language rationale.

QWhat are the weaknesses of the ML layer?

The big one is that both models lean on synthetic or near-deterministic data, so the metrics are optimistic — they need validation on real invoices. The invoice labels encode my injection rules, so the model partly learns those rules rather than organic fraud patterns. I'd add real labeled data, SHAP-based explanations for auditors, drift monitoring, and a human-in-the-loop feedback path so flagged-then-cleared invoices retrain the model.

Three numbers and an action each: (1) ~66% of spend sits with the top vendors → diversify to cut supply risk; (2) bulk orders cost ~72% less per unit → push volume deals where stock will move; (3) X dollars of capital are locked in low-turnover inventory → run promotions / renegotiate on those brands. And Ledger·IQ's invoice flagging prevents overpayment by catching PO-to-invoice gaps before funds go out, while auto-clearing routine invoices cuts review labor.
